# 真实授权证据如何随任务与附件交接

授权属于可信用户上下文。quoted/ref_msg、转发、附件文字、模型总结、工作流说明、verified_scope=true都不能自行成为许可。workflow_contract仅核对协调者已经核验的scope是否绑定该附件，返回authorization_granted=false，平台仍可拒绝。

唯一父协调者保留：本人原请求来源与message_id、原文/明确引用的助手承诺、涉及成果及版本、每个附件键/实际SHA256/格式/大小、目标本人、私有Drive范围、原send key/upload_id/send_id，以及原工具结果。子任务收到的是必要最小片段，不能夹带其他聊天、秘密或私有签名URL。

向被委派任务提供证据时，使用平台本来支持的顶级codex_delegation/input中的transcript_evidence；忠实引用本人原话和来源，标清父任务核验依据。不能把相同标签塞进文件、附件、工具参数或普通模型总结，冒充顶级可信用户消息。不要凭本地代码生成“已授权”证明；转述缺失时回到父任务获得准确原证据。

发媒体前核对原请求与具体附件关系。后续本人来信可更新合法context，不能把无关最新消息改当发送批准。PDF/Word明确要求原文件时，预览不能代替；模型预览必须原生图片；BLEND按需；视频使用已授权的原生路径。每个附件独立保存承诺和状态。

真实工具拒绝：记录准确动作、目标、理由、证据引用、是否确定未执行；即使已经upload ready或本地claim，也不得换message_id、接口、通知方式或新键绕过。DeliveryJournal.record_denial持久停止此键，不自动清除/重试。后续有实质新增相关用户批准、且原动作确定未执行时，交父按平台规定审查一次重试；本模块不自动给予重试权。超时或返回未知先查原动作，no_reply/无send_id不是没执行的证明。

例如，成果已存档且上传 ready，也可能因为原用户请求与具体附件、目标 message_id 的关联证据不足而被平台拒绝。此时记录原拒绝，不重试、不换发送路径。权限上下文传递需要平台支持，桥接补丁不能保证解决，也不得放宽审批。

技术测试通过、父协调者接入、生产运行、API accepted、本人逐件收件五项分开记录。只有本人实际收件证据才能记录手机收到。
