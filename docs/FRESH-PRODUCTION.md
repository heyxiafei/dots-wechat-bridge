# Approved future-only production

`fresh_after_approved_cutover` is an explicit candidate production mode for an
already bound, unused replacement installation. It does not require copying old
messages. It does not activate by installing, scanning, or passing offline tests.
The default `retained_state` flow and its history checks are unchanged.

The operator must first obtain the user's concrete cutover approval and actually
verify the existing writer is fenced, the original Tunnel route is selected, and
the original `weixin.message` subscription is being continued. The existing
private `runtime/setup-approval.json` records those actions and their evidence.
References are audit records, not remote isolation proofs; a local worker lock
also cannot prove remote exclusion. This mode introduces no fictional platform
verifier, new key, new subscription, or second service. Unconfirmed external
facts must remain unconfirmed and activation must not be performed.

The existing profile/client/key/startup checks still apply. The profile is
rendered with the additional explicit `--fresh-production` option to
`scripts/render-config.py`. Rendering prepares a configuration only. Its exact
approved command must be the installation's Python and `probe/probe.py`, the
installation's `runtime/state`, `--fresh-production`, and the authorized callback
host options. The profile must reference the exact approved original Tunnel.
No approval is generated by the renderer or runtime.

An empty replacement database does not contain the original callback URL or
subscription identity. Obtain these from an already authorized original
platform request/receipt or a supported platform readback. Observing an unrelated
new subscription is not original-route evidence. This implementation does not
invent a platform API, a callback URL, a hash, or an original subscription ID.
Whether the platform will resend the existing `events/subscribe` request after
the original Tunnel reconnects must be established on the real platform; the
offline implementation and the existence of a runtime key do not prove it. If
the original scope cannot yet be confirmed, this remains a separate deployment
prerequisite, and no production activation should be claimed.

The private approval retains `isolation_mode: old_writer_fenced`,
`approval_reference`, `isolation_evidence_reference`, `profile_sha256`,
`client_sha256`, and `startup_mode`. Its `handoff` uses these additional fields:

| Field | Meaning |
|---|---|
| `continuity_mode` | Exactly `fresh_after_approved_cutover` |
| `generation` | A unique 32-character hexadecimal identity for this approved cutover |
| `binding_sha256` | SHA-256 of canonical `[bot ID, owner ID, binding epoch]` |
| `approved_at_ms` | Actual time of the applicable approval, in milliseconds |
| `cutoff_ms` | Fixed lower bound, at or after approval; only later provider timestamps qualify |
| `tunnel_id` | Original Tunnel identifier, obtained from the authorized platform configuration |
| `subscription_id` | Original subscription identity, not a newly invented replacement |
| `route_sha256` | SHA-256 of compact JSON `['owner-only-tunnel', callback URL, 'weixin.message', {}]` using the existing subscription encoding |
| `platform_route_evidence_reference` | Reference to actual original route verification |
| `subscription_continuity_evidence_reference` | Reference to actual original subscription continuation evidence |
| `fresh_cutover_evidence_reference` | Reference to the explicit future-only scope approval |

`binding_sha256` uses sorted-key, ASCII, compact JSON through
`probe.fresh_production.binding_fingerprint`; it selects no credentials.
The approval file must be a regular, single-link, current-user file with no group
or other access, below a nonsymlink path. Whole approval content is pinned in the
database by digest. The runtime reads this same exact file; it never discovers
or reconstructs an approval from chat, booleans, database locks, or old snapshots.

First activation requires empty inbox, outbox, event queue, peers, attachment
and upload state plus an unused cursor. Existing bounded diagnostic state is
never promoted, reset or deleted. Activation persists the immutable generation,
cutoff, binding, subscription, route and approval digest. Restarts reuse them;
they cannot restart the cutoff at the current time or silently use a new binding.

The MCP process can start waiting for the original subscription. It performs no
Weixin polling or sending until that exact subscription completes a real callback
challenge in the current process. The cached verification shortcut is disabled
in this mode. Subscription expiry blocks processing until that same subscription
is refreshed. The mode does not delete, disable, recreate or redirect the
subscription; a webhook 410 terminates that event without changing subscription
records.

Raw owner, destination, direct-message type, complete-message state, provider
timestamp and source ID are evaluated before body, quote, context or media
handling. The source ID is the official lossless uint64 `message_id`, represented
by a decimal string or exact Python integer; `client_id` is not a substitute.
Missing, nonfinite, fractional, nonpositive or implausibly future timestamps
stop the batch and leave its cursor unchanged. This integer/time-window policy
is deliberately conservative; it does not assert the server guarantees clock
trust or ordering. Valid old owner records are skipped without body/media/context
processing. A mixed batch is checked item by item. The upstream may transmit old
payloads in `getupdates`; this mode does not claim to prevent that network receipt.

For eligible records, inbox, immutable admission, context provenance, media
references and provider cursor commit together. A duplicate source cannot change
its original timestamp or outgoing status. Event assignment, event POST, reply
enqueue, attachment enqueue, media processing, and send POST recheck admission,
binding and original subscription. The current context token must come from a
current-generation admitted message. Authentication rebinding requires a separate
reconciliation; it cannot silently revive old pending work.

Original stable event IDs, message IDs, final slots, attachment send IDs and
submission ledgers remain in use. Event delivery with an uncertain result is
terminal `delivery_unknown`; explicit rejection is terminal. Restarted attempted
events are not automatically replayed. Weixin unknown/rejected sends retain the
existing conservative semantics, never a new identity to force a resend.
Fixed system ACKs and source-less notifications are not enabled by this mode.

Rollback means stop this candidate, preserve its approval/profile/database and
all receipts, then reconcile. Do not copy an older approval or ordinary profile
over the generation. Older code rejects the explicit fresh option/unknown
continuity mode; current code refuses an ordinary production entry on a fresh
database. Never delete the fresh marker or admission ledger to make old code run.

Offline regression is separate from external cutover verification, original MCP
reachability, durable background operation, a new owner message, one normal
reply, and actual phone receipt. API acceptance alone is not delivery. This mode
does not itself supply runtime credentials, platform permissions, subscription
management capabilities, an official quota reader, or proof that another host
has stopped.

Protocol review reference: Tencent/openclaw-weixin commit
`874637a0dbc24050f72d1385add4fc6170a2d726`, `src/api/types.ts`,
`src/api/api.ts` and `docs/protocol.md`. Their client types permit absent metadata;
the local fail-closed policy above does not turn optional wire fields into an
invented server guarantee. No upstream install scripts or code are executed.
